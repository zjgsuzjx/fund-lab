# 基金练习室：功能清单与开发规划

状态：Figma V2 已由用户确认定稿；本文件作为首版开发范围和验收依据。

设计稿：https://www.figma.com/design/pCs35pDFqGsWtpc6YiXuDT?node-id=11-1023

## 一、产品目标与首版范围

做一个供个人在自己电脑上使用的基金投资模拟网站，用虚拟资金练习基金申购、赎回、费用计算和持仓管理。沿用已定稿的 12 张移动端页面，并适配电脑浏览器。

- 运行方式：本机运行，浏览器访问，无需购买服务器。
- 技术基础：React + TypeScript + Vite 前端，Python + FastAPI 后端，PostgreSQL 数据库。Python 使用 `environment.yml` 定义的 Conda 环境 `simulate-alipay`，不在仓库内携带运行时或虚拟环境。数据库使用电脑上独立安装的服务，项目通过 `.env` 连接自己的数据库；其余具体依赖版本在项目初始化时验证并锁定。
- 账户：本地用户名与密码；每个新账户一次性获得 100,000.00 元虚拟本金；账户之间数据隔离。
- 数据：先使用固定演示数据验证交易，再接入经验证可用的基金数据源。演示模式与真实数据模式明确区分，禁止同一账户混合结算。
- 基金范围：首版先支持交易规则已录入、净值可获得的普通境内开放式债券型、指数型和混合型基金；A/C 等份额按独立基金代码处理。
- “覆盖支付宝全部基金”不作为首版承诺。基金市场目录、支付宝代销目录、具备完整模拟交易规则的基金池是三种不同覆盖范围，应分别统计。
- 债券型基金属于首版范围；直接买卖国债、企业债等单只债券不属于首版。
- 首版不连接支付宝账户，不同步真实资产，不发生真实扣款。

优先级：P0 为首版必须完成；P1 为首版稳定后的增强功能；P2 为长期扩展。设计稿中的设置入口需要补充对应表单或弹窗后才能算实现完成。

首版未实现分红及特殊权益处理前，发现相关事件的基金应标记为暂不支持继续自动结算并提示原因，或从首版可交易池排除；不能长期静默忽略事件。扩大交易池需要交易规则覆盖，不只是新增基金名称。

## 三、交易与收益口径（开发前冻结）

1. 总资产 = 可用现金 + 买入在途 + 已确认基金市值（含仍在持仓中的冻结份额）+ 已确认赎回在途；每笔资产只能归入一项。
2. 买入申请在一个事务内减少可用余额并增加买入在途；正式净值可用后确认份额、落批次、扣费用并转出在途。
3. 卖出申请先冻结批次份额；确认时减少持仓并形成扣费后的赎回在途；到账时转为现金。
4. 净值缺失不能用昨日净值或盘中估值补成交。截图中的净值、费率和日期是演示样例，不能直接成为生产规则。
5. 申购和赎回的费用算法、精度及舍入以基金规则配置为准，禁止所有基金共用一套固定百分比。订单详情区分预估值和最终确认值。
6. 累计收益按总资产减净投入计算；初版没有额外充值/提现时，净投入为初始本金。后续引入资金变动必须计入净投入。
7. 持仓收益与收益率使用剩余批次成本定义，明确是否含申购费用。累计收益、已实现收益、未实现收益采用统一口径并能对账，不混用。
8. 不支持的基金类别、规则缺失或权益事件不可只做前端提示：后端必须拒绝不安全结算或禁止交易。

## 四、开发规划表

2026-09-13 进度：已打通前端、API 与 PostgreSQL，完成账户、基金、净值、自选基础表及命令行启动说明，见[开发指南](开发指南.md)。阶段 1 原列的规则、订单、批次、流水和任务表尚未建立，随规则核验和对应业务逐步补齐，不能将当前底座验收等同于整个阶段或交易能力全部完成。

| 3. 基金目录与数据展示 | 3–5 工作日 | 数据适配、缓存与同步；基金搜索/分类/排序/分页；详情与走势图；自选；交易规则和更新时间；空状态及失败状态 | 发现页、详情页、可查询基金数据、同步日志 | 演示/真实数据区分清晰；图表及规则与来源对得上；缺数据基金不会被误判可交易 |
| 4. 买入与确认结算 | 4–5 工作日 | 实现买入试算、预留资金、订单创建、日历截止规则、净值确认、生成批次、订单详情、撤单；幂等与并发处理 | 可完成一次模拟买入的纵向流程 | 覆盖截止前后、假期、余额不足、重复提交、缺净值、撤单/结算竞争；资金与份额对账通过 |
| 5. 卖出与资产账本 | 4–6 工作日 | 实现按批次赎回、持有期费率、冻结份额、确认与到账、撤单释放；持仓及收益计算；重启补结算和对账 | 可完成买入→持仓→卖出→到账的完整闭环 | 多批次/部分赎回/全赎回/费用分界/并发超卖测试通过；重启补处理不重复记账 |
| 6. 记录、设置与边界完善 | 3–4 工作日 | 交易搜索筛选与详情全状态；CSV 导出；账户设置；数据备份恢复；六类边界反馈及其他错误；清理无效入口 | 完整 12 页、必要二级弹窗、导出与备份工具 | 所有定稿入口有结果；导出内容正确；从备份恢复后账户、订单、份额、流水一致 |
| 7. 联调、验收与本地交付 | 3–5 工作日 | 按交易场景回归；核对真实源样本；移动/电脑浏览器检查；鉴权与输入安全；启动停止、关机重启、任务重试、升级迁移演练；修复问题 | 本地可用版本、操作手册、已知限制、验收记录 | 从启动→注册→搜索→买入→确认→卖出→到账→导出完整通过；核心账本无差异，严重问题清零 |

估计合计：24–35 个专注工作日。个人业余开发应根据每周可投入时间换算日历周期，暂不设置固定上线日期。

### 阶段里程碑

- 阶段 2 完成：能注册、登录，有可用界面骨架。
- 阶段 3 完成：能浏览、搜索、收藏基金，查看净值与规则。
- 阶段 4 完成：能买入并等待确认，资金与份额正确。
- 阶段 5 完成：买卖与资金到账闭环可运行。
- 阶段 7 完成：个人本地可用首版，带备份与操作说明。

## 五、关键验收场景

| 场景 | 必须验证的结果 |
|---|---|
| 新用户连续点击注册 | 只有一个账户及一笔 100,000 元初始本金流水 |
| 两次并发买入合计超过余额 | 不能双双成功导致负余额 |
| 交易日截止前后及假期下单 | 净值归属日和确认日符合配置的日历规则 |
| 应确认日净值未到 | 保持等待，资金与份额不错误转移 |
| 撤销申请恰好碰上结算任务 | 只有一种最终结果，既不双退款也不重复确认 |
| 不同日期买入多批份额后部分卖出 | 批次分配、持有天数、费用和剩余成本正确 |
| 两次并发卖出同一批份额 | 冻结份额不被重复卖出 |
| 卖出确认但未到账 | 金额位于赎回在途，尚不可用于新的买入 |
| 关机数日后启动 | 自动补处理已具备净值和规则的历史订单；再次启动不重复处理 |
| 数据源重复、缺失、修订或断网 | 幂等同步；合理等待/拒绝；保留依据，不静默篡改已确认流水 |
| 尝试读取另一个账户的订单 | 后端拒绝，不依赖前端隐藏按钮 |
| 备份后恢复至测试数据库 | 用户、订单、持仓批次、余额与流水一致 |

## 六、执行方式

每阶段开始时选定具体任务和验收样例；完成后提供可运行结果及简短验收记录。交易引擎使用自动化测试覆盖金额、日期、并发与状态转换；界面以关键流程验证和截图比对为主。无需为静态文案堆叠测试。

当前可以开始阶段 0。优先验证数据字段和交易口径，再搭工程；页面开发可使用确定性的演示样本推进，但真实数据模式必须独立完成验证后启用。
